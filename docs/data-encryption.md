# 대화·첨부 파일 저장 암호화

메신저 서버가 **대화 내용**과 **첨부 파일**을 디스크·DB에 저장할 때 암호화합니다 (AES-256-GCM).
화면과 앱 사용 방식은 달라지지 않습니다. 복호화 키는 서버를 운영하는 쪽(당사)이 직접 만들어 보관합니다.

## 범위

| 대상 | 암호화 | 비고 |
| --- | --- | --- |
| 대화 내용 (`Message.content`) | O | DB에 암호문 저장, 읽을 때 서버가 자동 복호화 |
| 삭제·만료 보존 원본 (`MessageArchive.content`) | O | 위와 동일 |
| 첨부 파일 (uploads 볼륨) | O | 파일 전체를 암호화해 저장, 내려받을 때 복호화 |
| DB 백업(`scripts/backup-db.ps1`) | 대화 내용은 암호문 | 덤프에 대화 내용은 암호문으로 들어감. 이름·이메일·방 이름 같은 메타데이터는 평문 |
| 프로필 사진, 파일명·파일 크기, 방 이름 등 | X | 대화·파일 내용이 아니어서 대상 아님 |

## 켜는 순서

1. **키를 직접 만든다** (서버나 본인 PC의 터미널에서): `openssl rand -hex 32`
   - 이 값은 채팅·메일·저장소에 붙이지 않는다.
2. 키를 **서버 밖에도 안전하게 보관**한다 (비밀번호 관리자, 봉인된 문서 등).
   **키를 잃으면 암호화된 대화·파일은 복구할 수 없다.**
3. 메신저 `.env`에 `DATA_ENCRYPTION_KEY=<키>` 를 넣고 서버를 재시작한다.
   - 관리자 설정 > 보안 정책의 "저장 암호화"가 "사용 중"으로 바뀌면 적용된 것이다.
   - 이때부터 새로 쓰는 대화·올리는 파일이 암호화된다. 기존 데이터는 평문으로 남아 있어도 그대로 읽힌다.
4. **기존 데이터 변환** (선택, 권장): DB 백업과 uploads 볼륨 백업을 받은 뒤 실행한다.
   ```
   # 먼저 몇 건이 변환 대상인지만 확인 (아무것도 바꾸지 않음)
   docker exec -w /app csintech_messenger-server-1 node --input-type=module -e "import('./src/lib/encryptExisting.js').then(m=>m.encryptExisting({dryRun:true}).then(console.log))"
   # 실제 변환
   docker exec -w /app csintech_messenger-server-1 node --input-type=module -e "import('./src/lib/encryptExisting.js').then(m=>m.encryptExisting({dryRun:false}).then(console.log))"
   ```
   몇 번 실행해도 안전하고, 중간에 멈췄으면 다시 실행하면 이어서 진행한다.

## 주의

- 키가 없거나 다른 키로 서버를 띄우면 암호화된 대화는 "[복호화할 수 없는 내용]"으로 보이고 첨부 파일은 내려받을 수 없다. 데이터는 그대로이므로 맞는 키를 다시 넣으면 복구된다.
- 키 형식이 올바르지 않으면 서버가 시작하지 않는다 (잘못된 설정으로 평문 저장되는 것을 막기 위함).
- 키를 바꾸는(회전) 기능은 아직 없다. 키를 바꾸면 기존 암호화 데이터를 읽을 수 없으므로 임의로 바꾸지 않는다.
- 대화 내용이 암호화되면 서버가 DB에서 내용을 직접 검색할 수 없어, 대화방 검색과 감사 조회의 내용 검색은 최근 대화부터 풀어서 찾는다
  (대화방 검색은 최근 1만 건, 감사 조회는 조건에 맞는 최대 5만 건까지 살핀다). 아주 오래된 대화는 검색되지 않을 수 있다.
- 첨부 파일은 보관 기간이 지나 서버에서 지워질 때까지 uploads 볼륨에 암호화된 상태로 남는다.
  uploads 볼륨은 DB 백업에 포함되지 않으니 필요하면 별도로 백업한다 (백업본도 암호화된 상태).
